这是第一轮。请按自己的席位研究视角独立检索、思考，并对 research_brief.md 里的问题提出一个你自己的初步解法。不要读取或等待其他席位的意见。

先判断问题到底卡在哪一步：是信息不够、是缺某个做法、是资源不够、还是现有做法有已知的失效条件。把你的解法对准那个卡点，而不是对准问题表面。

中文正文建议约 800–1500 字，重点写：

1. 一句话主张：用什么做法解决哪一部分问题，以及它的适用条件。
2. 具体做法：按可执行的顺序写清步骤，标出每一步需要什么（数据、工具、权限、时间）。别人应该能照着做。
3. 它为什么成立：机制论证或已有实测依据。有式子先定义符号和假设，说明哪一步是推断而非已证。
4. 至少三份核查过的一手资料：每份写清它测了什么、结论是什么、读到的层级，以及它支撑你方案的哪一步。若你的做法就是某篇已有方法，直接说明并给出该文献。
5. 前置条件与最可能失败的地方：在什么条件下这个方案不成立；哪个环节最容易出问题。
6. 检索词、检索范围与尚未核查的部分。

正文末尾附一个合法 JSON 代码块，按真实情况填写。agent_id 必须是你自己的席位 ID（见系统提示），`design_id` 为 `D-` 加自己的 ID：

```json
{
  "agent_id": "你的席位ID",
  "round": 1,
  "design_id": "D-你的席位ID",
  "title": "你的初步解法名称",
  "evidence_urls": ["实际核查过的URL一", "实际核查过的URL二", "实际核查过的URL三"],
  "retrieval_status": "completed 或 partial"
}
```

`retrieval_status` 必须如实填写，三选一：

- `completed`：你确实读到了至少三份一手资料的方法段/结果段，并且查过至少一个“这个做法已知在什么条件下失效”的方向，能说出检索词与范围。
- `partial`：检索做了，但明确知道还有未覆盖的部分（例如某个关键前提没查到依据、只读到摘要、时间不够）。选它不扣分，`audit` 会把你列进 `retrieval_partial_seats`，终稿会照实写。
- `blocked`：检索根本没做成。此时该席位会被记为未完成，不把它当成有证据支撑的解法。

**不要为了好看写 `completed`。** 选 `partial` 是安全的，它只是要求你在正文里说清缺什么。
