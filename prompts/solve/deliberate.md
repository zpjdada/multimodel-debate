这是中间轮（不是最后一轮，也不是投票轮）。你已能看到其他席位此前各轮的原文。请做三件事。

## 一、检索（不能省）

本轮必须重新检索，不允许只凭已有印象评审。至少做两轮不同角度的查询，并在正文里列出你实际用过的查询词、查到的范围、以及读到了哪一层（完整方法段/部分正文/仅摘要）。重点查的是：

- 你打算批评或合并的那条做法，是否有人已经试过、结论如何、在什么条件下失败过；
- 你方案里最关键的那个前提，有没有实测或官方文档支撑；没有的话，它就是整条方案的薄弱点。

自己此前的检索结论可以被推翻，但不能因为别人这么说就接受——关键文献自己打开方法段核对。

## 二、互评

至少实质回应两个其他席位。写清你针对的是哪条具体主张、你的立场（支持/反对/建议修改）、论据，以及什么证据能推翻你现在的判断。不要为了辩论强行反对，也不要为了和气强行支持。

特别注意两类问题：一条方案看起来成立，但它的前置条件在 research_brief.md 写明的资源下根本满足不了；或者它的步骤本身没错，却没有解决 research_brief.md 指出的那个卡点。这两类都应该直接说出来。

## 三、收敛：合并、拆开或收窄

本轮允许你把几条互补的初步解法合并成一条更完整的方案，条件是合并后的步骤仍然是**一件在给定资源下做得完的事**，而不是把几个方向捆在一起。

合并时写清：

- 合并了哪些初步解法、保留了哪条核心机制；
- 合并后覆盖了原来各自都覆盖不到的那一部分是什么（如果只是“两件事都做”，那不算合并）；
- 合并后新增了哪些前置条件。

如果你认为自己的解法不成立、已被更简单的做法覆盖，或它的前提在给定资源下满足不了，直接说出来并给证据。允许本轮结束时你的方案被你自己放弃或收窄——这是有效结果，不是失败。也可以只保留原方案中最关键的一步。

## 输出

中文正文，建议 900–1600 字。正文末尾附一个合法 JSON 代码块，按真实情况填写：

```json
{
  "agent_id": "你的席位ID",
  "round": 本轮轮次,
  "searched_queries": ["实际用过的查询一", "实际用过的查询二"],
  "evidence_urls": ["本轮实际读到的关键资料URL"],
  "responses": [
    {"to_agent": "其他席位一", "stance": "support", "claim": "针对哪条主张、为什么，附正文证据"},
    {"to_agent": "其他席位二", "stance": "modify", "claim": "针对哪条主张、建议怎么改，附正文证据"}
  ],
  "merges": [
    {"designs": ["D-其他席位"], "into": "合并后的一句话做法", "why": "合并后覆盖了什么原来覆盖不到的"}
  ],
  "withdraws": ["如果你放弃或收窄了自己的解法，写在这里；没有就留空数组"]
}
```

`searched_queries` 至少两条，且必须是你本轮真的敲进检索工具的查询——`audit` 会检查条数，终稿会照实引用。`merges` 和 `withdraws` 没有就写空数组，不要编造。本轮不投票，不要输出 votes。
